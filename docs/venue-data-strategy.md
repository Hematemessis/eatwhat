# 餐厅数据与 AI 决策方案

## 当前现状

- 首页 Demo 的 `/api/demo/synthesize` 从本地 JSON 读取 56 个候选地点，其中南山区 43 个、福田区 13 个；这是一套演示降级数据，不是实时数据库。
- `packages/venues` 已有 Google Places 与 Yelp 适配器，但完整系统的触发接口仍是 SQLite 模式下的 stub，线上首页 Demo 也没有调用这两个适配器。
- DeepSeek 当前只负责理解成员偏好并对候选地点排序；它没有在本项目中执行实时地图检索。

## 推荐架构

```text
用户输入区域与偏好
        ↓
地图 POI 服务召回 20–40 个当前候选
        ↓
服务端规范化、去重、过滤硬约束
        ↓
DeepSeek 对候选集做群体匹配、排序与解释
        ↓
展示推荐理由、未满足约束和地图跳转
```

中国大陆首选高德 Web 服务 API。它提供关键字搜索、周边搜索、行政区过滤和 POI 详情，适合完成“候选召回”；DeepSeek 继续负责偏好理解、冲突分析和推荐解释。不要让大模型自由联网搜店并把搜索文本直接当数据库，因为商家位置、营业状态、评分和价格很难稳定校验，也难以保证来源一致。

## 分阶段落地

1. **演示阶段（当前）**：明确标注“深圳 56 家演示样本”，其他地区不宣称为实时搜索；本地数据只作为 API 不可用时的降级方案。
2. **实时召回 MVP**：申请高德 Web 服务 Key，在服务端用地理编码把用户区域转换为经纬度，再用餐饮分类做周边搜索；候选结果限制在 20–40 条后交给 AI 排序。
3. **质量控制**：记录数据源、查询时间和候选数量；过滤无地址、低信息量、距离过远和明显重复的 POI；推荐页展示地图来源与跳转链接。
4. **规模化**：增加配额监控、超时与降级，不把地图 POI 批量沉淀成自建数据库。若业务需要长期存储或二次加工，应先与地图供应商确认授权范围。

## 接入时需要的配置

- `AMAP_WEB_SERVICE_KEY`：仅在服务端使用，不暴露给浏览器。
- 地理编码请求：把“深圳南山区”等区域转为坐标。
- 周边搜索请求：使用餐饮 POI 分类、半径、综合排序与分页。
- DeepSeek Tool Call（可选）：让模型提出搜索参数，由服务端实际调用高德；模型本身不直接执行网络请求。

## 验收标准

- 输入深圳以外城市时，候选商家来自对应城市并带可打开的地图链接。
- 推荐结果中的名称、地址、距离和数据来源可追溯到同一次 POI 查询。
- 地图服务失败时明确提示已降级到演示数据，不混淆实时结果与离线样本。
- AI 只能从召回候选集中推荐，不能编造列表外商家。
